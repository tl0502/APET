## 4. 4 个开放项（brainstorm 必须先决，不然 plan 无法精确）

### Open-1: `.soul/` 目录字段表 schema

spec §3 + §11 给了粗略描述（manifest.toml + identity.md + style.toml + initiative.toml + memory.toml + examples.md），但每个 section 的字段、必填/选填、类型、长度限制都没敲死。

ADR-028 要敲：
- `manifest.toml`: schema_version / id / name / version / description / source（'builtin' | 'user' | 'imported'）/ created_at — 还要不要 author / license / tags？
- `identity.md`: 自由 markdown vs 强 schema？字符上限？
- `style.toml`: 字段表（tone / formality / verbosity / 拒答风格 / emoji 用法 …）
- `initiative.toml`: idle 触发阈值 / 主动话题白名单 / quiet hours
- `memory.toml`: KV 注入策略 / fact 提取频率
- `examples.md`: few-shot 上限条数？格式约束？

### Open-2: SoulValidator deny 字段完整清单

spec Constitution #11 说"Soul 不能含 permissions / tools / safety_prefix"，但具体禁用字段名要 enumerate：
- `manifest.[permissions]` / `manifest.[tools]` 整段拒
- `safety_prefix` / `safety` / `system_prefix` 命名变体怎么穷举？regex 匹配 `^safety_` / `^system_`？
- 错误码 `SoulValidateError::ForbiddenField(field_name)` 是否需要细分（permissions vs tools vs prefix）？

### Open-3: LegacyUnknownSnapshot.identity_prompt 字面文本

migration 004 cascade backfill 把老 conversation `persona_id='momo'` 但缺 snapshot 的情况兜底到 LegacyUnknownSnapshot。这个兜底 snapshot 的 `identity_prompt` 是用户对话时看到的人格自述 —— 字面是什么？

候选思路：
- "（系统）此对话的人格信息已遗失或损坏，桌宠以中性默认形象继续。可在设置中重新绑定。"
- 还是更亲和："（桌宠）唔，我有点忘了之前的样子，要不你帮我重新选一个性格？"
- 还是空 prompt + UI 层 banner 提示？

### Open-4: ConvPersonaStatus 4 状态 UI 文案

spec §2.5.2 定义 4 状态：CurrentlyBound / SamePersonaOutdated / DifferentFromActivePersona / NoActivePersona（具体枚举名以 spec 为准）。每个状态在 UI 显示的提示语 + 允许动作还没敲：
- SamePersonaOutdated: "你已修改 X 人格的最新版本，要把此对话升级到新版吗？[升级] [继续用当前快照]"
- DifferentFromActivePersona: "此对话用的是 X 人格的快照 vYYYY-MM-DD，与你当前 active 人格 Y 不同。[切换 active] [fork 出新对话用 active]"
- ...

## 8. A0 → A1 移交风险清单（已知陷阱）

- **`.soul.md` 单文件 legacy 路径**: spec §11 提到兼容支持，但 A1 不强求实施；先做 `.soul/` 主路径 + `.soulpack` 分发路径，单文件 legacy 推到 A1 收尾或 P1
- **内置 3 人格迁移**: momo / joker / coach 当前是什么形态？需要先 `Read` 一下 `personas/` 目录看现状再决定迁移工作量
- **migration 004 是 multi-step ALTER**: SQLite NOT NULL ALTER 必须两步（先 nullable column → backfill → 再 NOT NULL），spec §12.0 已给 SQL 模板，照抄即可，但 test_db.rs apply 必须跟（lessons §17 教训）
- **fork_conversation 跨 conversations + messages + persona_rebind_audit 是 tx 注入式典型场景**: 见 lessons.md §15（#29 落地的 tx 注入模式），A1 直接复用
- **A1 工作量 ~1.5w 是 spec 估值**: A0 实际 ~2 天 vs spec 估 ~1w 大约 1:3.5 的偏差比例（spec 偏保守）；A1 真实落地可能 3-5 天
